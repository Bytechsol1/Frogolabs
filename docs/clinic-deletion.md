# Clinic deletion

Platform administrators can open **Dashboard → Clinics → clinic actions (⋯) → Delete Clinic**. The existing View Patients, Disable and Re-enable actions remain. The deletion dialog lists the permanent effects and requires the clinic's exact name. Cancel and a mismatched name never send a deletion request. Failures leave the clinic visible with an error and allow retry. A confirmed success removes the row and updates totals; an older in-flight list response cannot restore the deleted row.

`DELETE /api/v1/clinics/:id` requires a verified platform administrator JWT and JSON `{ "confirmationName": "Exact clinic name" }`. Clinic managers cannot delete clinics. Unknown clinics return 404, invalid confirmation returns 400, and a clinic containing a platform administrator account returns 409; move that account's membership first. Deleted staff cannot reuse their old JWTs because protected requests look up the current user in PostgreSQL.

The service deletes only the selected clinic's application records in one PostgreSQL transaction: sandbox jobs, local Terra order records, lab results, report access records and stored report bytes, notifications, session history, workflows, patients and health metrics, staff accounts, verification challenges, logo bytes, branding and the clinic itself. Existing database cascades remove stored files and related access records; no migration is required. The supported live configuration stores logo/report bytes in PostgreSQL. Historic files on a separate filesystem or at an external provider are outside this database operation.

Per-email signup send/cooldown buckets are cleared for released addresses so a fresh clinic can immediately register with the same email. IP rate limits remain. Pending email changes belonging to deleted staff are also removed. If another clinic or platform account independently uses the contact email, its account, verification challenge and rate limits are preserved; deletion never frees someone else's email. Other clinics' data survives, with existing nullable uploader/author references cleared by the database when necessary.

Clinic and child-row locks coordinate deletion with writes. OTP issuance also holds a user-row key-share lock, preventing a concurrent resend or email change from creating a challenge for a deleted account. Any transaction failure rolls back the operation. Global Terra webhook deduplication records are preserved. This action does not cancel external lab orders or delete Validic/provider accounts.

From the repository root, run `npm run test:clinic-delete --workspace=backend` with Docker Desktop available. It creates and removes a fresh loopback-bound PostgreSQL container, uses real JWT authorization and synthetic records, and never loads application `.env` files. Tests cover permission checks, confirmation, active/disabled/empty clinics, stored-data cascades, tenant isolation, platform-account protection, rollback, JWT revocation and immediate same-email registration. The email regression suite remains `npm run test:email --workspace=backend`.

After `npm run build:frontend`, `node backend/scripts/browser-email.cjs` checks the admin menu and dialog, cancellation, typed confirmation, server-failure retry, duplicate-click protection, stale list responses and hidden delete controls for clinic managers, along with the existing authentication flow. All browser API responses are synthetic; no real clinic is deleted or email sent.
